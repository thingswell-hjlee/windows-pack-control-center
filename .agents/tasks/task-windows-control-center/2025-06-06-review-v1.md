# Windows Local Web Control Center for AIBox Devices

A greenfield .NET 8 gateway and React/TypeScript dashboard for monitoring industrial AI camera boxes over MQTT. The gateway receives events and heartbeats from AIBox devices via per-device MQTT connections, normalizes them into a unified schema, persists to SQLite, and pushes real-time updates to the browser via SignalR. The frontend is a Vite-built SPA served as static files from the gateway on port 8088, with CRUD management for devices/cameras, event filtering, CSV export, and a dashboard summary.

**Watch for:** The frontend expects paginated event responses shaped as `{ items, total, ... }` but the backend returns `{ data, total, ... }` — the Events page and Dashboard will render empty (confirmed). MQTT credentials are stored in plaintext in SQLite with no encryption and transmitted via unauthenticated REST endpoints (confirmed). The MQTT reconnection handler captures a stale `Device` object and a `CancellationToken` that may be cancelled, creating a potential infinite-retry or silent-failure loop (likely).

## High-level view

The gateway is structured as a single ASP.NET Core process running three `BackgroundService` instances that coordinate through `System.Threading.Channels`. `MqttReceiverService` maintains one MQTT client per registered device, routing messages into event or status channels based on topic substring matching. `EventNormalizerService` and `DeviceStatusService` consume from those channels, persist state, and broadcast through a SignalR hub. The unbounded channels and per-message DB scope creation will need attention if device density grows beyond a handful of devices.

The REST API surface is a standard CRUD layer on top of EF Core with SQLite. There is no authentication or authorization on any endpoint — device credentials, ONVIF passwords, and event acknowledgment are all accessible to anyone who can reach port 8088. The CORS policy binds on `0.0.0.0`, which exposes the API to the full network segment rather than just localhost.

The frontend is cleanly structured React with TanStack Query, SignalR integration, and Tailwind styling. The critical functional gap is the response shape mismatch: the backend returns paginated events under a `data` key while the frontend destructures `items`, so the event list and dashboard recent-events panel will always be empty until one side is adjusted.

The build pipeline outputs a self-contained win-x64 executable with the SPA baked into `wwwroot` by convention. The build order dependency (npm must run before dotnet publish) is implicit and fragile — if violated, the gateway ships without a frontend.

<summary>Issues (7)</summary>

1. **Paginated response shape mismatch** — Backend returns `{ data: [...] }` but frontend expects `{ items: [...] }`. Change the backend to return `items` or update `PaginatedResponse<T>` in the frontend.
2. **No authentication on any endpoint** — CRUD endpoints for devices, cameras, and event ack are fully open. Add at least a shared secret or basic auth for write operations, or document this as an accepted risk for LAN-only deployments.
3. **Plaintext credential storage** — MQTT passwords and ONVIF passwords are stored and returned in cleartext over HTTP. At minimum, omit password fields from GET responses and consider encrypting at rest.
4. **MQTT reconnect with stale state** — The `DisconnectedAsync` handler captures the original `Device` entity and the service's `CancellationToken`. If the device config changes between disconnect and reconnect, the old config is used. If the token is cancelled, the `Task.Delay` throws into an unobserved context.
5. **Timestamp string comparison for date filtering** — `EventsEndpoints` compares ISO timestamp strings lexicographically, which only works if all stored timestamps use identical UTC offset formatting. Store timestamps as a proper `DateTime` column or use `TsMs` for range queries.
6. **Unbounded channels with no backpressure** — `Channel.CreateUnbounded` means a burst of MQTT messages queues indefinitely in memory. Add a bounded capacity with a drop-oldest policy or log a warning when the channel falls behind.
7. **No test coverage** — There are no unit or integration tests. The event normalizer's deduplication logic, the heartbeat timeout behavior, and the CRUD validation paths are all untested.

## MQTT connection management and reconnection

`MqttReceiverService` polls the database every 30 seconds for enabled devices with MQTT hosts, then connects to any it hasn't seen yet. Each client's `DisconnectedAsync` handler removes the device from `_clients` and immediately attempts reconnection after a 5-second delay. Several issues compound here.

The handler captures the original `Device` entity by closure. If the user edits the device's MQTT host or credentials between disconnect and reconnect, the service reconnects with stale configuration — the updated row won't be picked up until the next 30-second poll creates a fresh connection (but only if `_clients` no longer contains the key, which the disconnect handler already removed). The net effect is a race between the reconnect closure and the polling loop that could result in duplicate connections or connections with outdated credentials.

The `stoppingToken` captured in the disconnect handler becomes problematic during shutdown. If an external broker disconnects the client at the same moment the service is stopping, `Task.Delay` throws `OperationCanceledException` which propagates as an unobserved task exception because the handler is `async void` in MQTTnet's callback model.

Additionally, `_clients` is a plain `Dictionary<string, IMqttClient>` accessed from multiple async contexts (the polling loop, disconnect handlers, and `StopAsync`). There's no synchronization, so concurrent modifications could corrupt state or lose entries.

## Event normalizer deduplication and timestamp handling

Event deduplication uses a composite ID: `{deviceId}-{tsMs}-{eventType}-{cameraId}-{trackId}`, checked with `AnyAsync` before insert. If the MQTT broker delivers the same message twice (QoS 1 at-least-once), two concurrent deliveries could both pass the existence check and attempt to insert — the second would throw an unhandled primary key violation. Wrapping the check-and-insert in a transaction or handling `DbUpdateException` for duplicate keys would make this robust.

The `Timestamp` field is stored as a string (ISO 8601). The events endpoint filters by date using `CompareTo` on the string representation of the parsed date. This only produces correct results if every stored timestamp uses the exact same format (e.g., always `Z` suffix, never `+00:00`). The normalizer stores whatever `timestamp` value comes from the MQTT payload, falling back to `DateTime.UtcNow.ToString("o")`. If any device sends a non-UTC timestamp or a different ISO variant, range queries will silently return incorrect results.

## Frontend-backend response shape mismatch

The backend `EventsEndpoints` returns:
```csharp
return Results.Ok(new { data = events, total, page = pageNum, ... });
```

The frontend `PaginatedResponse<T>` type expects:
```typescript
export interface PaginatedResponse<T> {
  items: T[];
  total: number;
  page: number;
  page_size: number;
}
```

The `Events` page accesses `data.items.map(...)` and the `Dashboard` accesses `recentEvents?.items?.map(...)`. Both will always see `undefined` because the JSON has a `data` property, not `items`. The optional chaining prevents a crash but the lists render empty.

## Security posture: no auth, plaintext credentials

Every REST endpoint is unauthenticated. The Device and Camera models include MQTT credentials and ONVIF credentials respectively. A GET request to `/api/devices` returns all fields including `mqtt_password` and `onvif_password` in cleartext. The CORS policy binds on `0.0.0.0`, meaning any device on the LAN can read and modify device configurations.

The risk escalates if this gateway is ever exposed to a wider network: an attacker gains MQTT broker credentials, ONVIF camera credentials, and the ability to acknowledge safety-critical events (clearing "unconfirmed" status on FALL_DETECTED or HAZARD_PROXIMITY alerts). The `AckRequest` record accepts any string as `AckUser` with no validation — there's no concept of an authenticated user behind acknowledgments.

## Resource lifecycle: unbounded channels

Both channels are created with `Channel.CreateUnbounded<MqttMessage>()`. If the normalizer or status service processes messages slower than they arrive (e.g., SQLite write latency under burst), the channel buffers grow without bound in memory. A misconfigured device sending thousands of events per second would OOM the process with no backpressure signal or warning log.
